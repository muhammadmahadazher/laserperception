# LaserPerception v0.3.0 release notes

Release date: 2026-08-26

LaserPerception v0.3.0 is the release boundary for the completed M6 KITTI Raw cross-domain
validation work. It adds dataset/reconstruction support, frozen-detector characterization, a
structurally widened TensorRT input profile, ROS replay and projected-reference integration
evidence, and the complete M6 technical record. It does not introduce a new detector or a new
scientific milestone.

## What changed since v0.2.0

v0.2.0 added compatible raw XYZ PointCloud2 ingestion and time-aware multi-sweep reconstruction for
the existing nuScenes deployment path. v0.3.0 applies the same frozen detector boundary to official
KITTI Raw data in a preregistered cross-domain study and validates the corresponding ROS integration
against committed same-platform projected references.

The lightweight Python wheel remains independent of ROS, CUDA, TensorRT, and OpenMMLab. KITTI,
nuScenes, the pretrained checkpoint, ONNX, TensorRT engines, and GPU/ROS environments remain
external.

## KITTI Raw support and M6a

M6a added official KITTI Raw decoding and the Raw-devkit pose/calibration arithmetic, froze the
proper KITTI-Velodyne-to-detector-frame rotation, and reconstructed deterministic model-ready
multi-sweep inputs without initializing the detector.

The first Tier-A oracle compared synchronized Raw OXTS and KITTI Odometry as though they were one
timing product and failed. That failure remains preserved. R1 established that they are distinct
official products. Prospective Protocol R2 then compared like with like and passed 271/271 exact
Raw-devkit pose comparisons on the diagnostic drive, 108/108 exact transfer comparisons on the
canonical reconstruction drive, exact raw decoding, and 24/24 deterministic offline reconstruction
targets over ten repeats each. No tolerance was relaxed to obtain the accepted result.

See the [M6a R2 result](../m6/M6A_RESULTS_R2.md),
[KITTI Raw contract](../m6/KITTI_RAW_CONTRACT.md), and
[model-frame alignment](../m6/MODEL_FRAME_ALIGNMENT.md).

## Frozen cross-domain characterization and M6b

M6b ran the unchanged official pretrained nuScenes PointPillars detector—without training or
fine-tuning—on 428 current KITTI Raw frames reconstructed under both H10 and H5. All 856 conditions
completed under the owner-approved frozen Protocol R2.

At score 0.25 and oriented BEV IoU 0.50:

| Class | H10 recall | H5 recall |
|---|---:|---:|
| Car | 0.242 | 0.727 |
| Pedestrian | 0.553 | 0.677 |

H10 versus H5 is a **compound temporal-and-density history ablation**. It changes temporal span,
`time_lag`, accumulated points, occupied pillars, and aggregation patterns together. The study does
not establish temporal span alone as the cause and does not claim H5 is universally superior. The
40,000-voxel retention cap was not supported as the primary corpus-wide explanation for the H10
recall deficit.

These metrics are annotation-conditioned against the available Raw tracklets. They are not
official KITTI benchmark AP or a physical false-positive rate. See the
[M6b final result](../m6/M6B_RESULTS.md).

## TensorRT structural profile remediation

The historical M2 engine accepted at most 30,000 voxels while the pinned preprocessing contract may
retain 40,000. The original M6b run therefore stopped before network execution when a valid input
exceeded the historical profile; it produced no evaluation predictions.

A prospective remediation rebuilt only the TensorRT optimization profile from the byte-identical
ONNX. MIN/OPT/MAX changed from 4,352/18,207/30,000 to 4,352/18,207/40,000. The model, precision,
weights, ONNX, postprocessing, thresholds, class mapping, and voxel geometry remained frozen. The
candidate passed the required nuScenes, non-evaluation KITTI, same-session profile, and repeatability
gates before M6b Protocol R2 was frozen. The wider profile is structural support only: **no latency
or performance claim is made from the rebuild**.

The engine remains an external, hash-pinned artifact and is not a v0.3.0 release asset.

## ROS projected-reference validation and M6c

M6c first required byte identity against the original M6a serialized matrices. R2 passed frame 0
and failed frame 1, then stopped. D1 showed that slightly non-orthonormal serialized rotations cannot
pass unchanged through ROS TF's unit-quaternion/SO(3) representation. Real tf2 was float32-faithful
to the projected representation; this diagnosis did not rescue R2 or introduce a tolerance.

Prospective R3 froze same-platform projected references before canonical live output. Final results:

- Gate 1A: 24/24 exact;
- Gate 1B: 856/856 exact;
- unique live conditions: 860/860 exact;
- exported detections: 113/113;
- bidirectional high-confidence coverage: 81/81;
- all continuous metrics: 81/81;
- class mismatches: zero;
- continuous outliers: zero; and
- `Detection3DArray` conversions: 10/10 exact under the accepted message contract.

The projected hashes are qualified to the pinned WSL2/Linux arithmetic and ROS environment; they
are not claimed portable across arbitrary platforms. See the
[final M6c R3 result](../m6/M6C_RESULTS_R3.md).

## What did not change

v0.3.0 does not change the official pretrained PointPillars checkpoint, detector architecture,
ONNX graph, FP16 semantics, postprocessing, score threshold, class mapping, deterministic
voxelization semantics, or voxel geometry. It adds no training, fine-tuning, second detector, INT8,
tracking, camera fusion, localization, vendor driver, custom CUDA, or optimization campaign.

The original M6a Tier-A failure, M6b 30k-profile structural stop, M6c R2 failure, and D1 diagnosis
remain visible. Accepted prospective protocols do not rewrite those historical outcomes.

## Performance scope

M6 was correctness and characterization work. It did not run a ROS latency campaign or establish
real-time operation. The 40k TensorRT profile rebuild has no attached latency or speed claim. All
historical performance figures remain qualified to their original workload, protocol, hardware,
and environment; none should be interpreted as KITTI Raw throughput.

## Limitations

This release does not provide official KITTI benchmark AP, physical-LiDAR validation, universal H5
superiority, projected byte-hash portability, arbitrary sensor calibration, localization, odometry,
per-point deskew, training/fine-tuning, production readiness, or safety certification. KITTI Raw
tracklet coverage is incomplete for the full LiDAR world, so the reported precision/AP-style values
are annotation-conditioned rather than official benchmark measures.

M5 remains conditional and inactive. No M7 or other technical submilestone is active.

## Installation and quickstart

The user-facing invocation did not change. Continue with the
[v0.2.0 raw/model-ready quickstart](../QUICKSTART_V0_2.md); it remains structurally valid for v0.3.0.
The versioned name records the release in which the raw interface was introduced rather than a
different command surface.

## Upgrade notes from v0.2.0

Existing lightweight-core, model-ready, and compatible raw PointCloud2 users do not need to change
their invocation. Rebuild/install the 0.3.0 package metadata as usual. KITTI Raw users should follow
the frozen contracts and external-data requirements linked above. Do not substitute the wider M6
engine profile for the historical M2 engine when reproducing M2 evidence, and do not infer that the
40k profile changes detector semantics or performance.
